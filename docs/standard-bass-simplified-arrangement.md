# Standard-bass simplified arrangement

`model::standard_bass_arrangement::arrange_standard_bass` and the full/viewer WASM export `arrange_standard_bass(scoreJson, optionsJson)` create a reviewable simplified edition. The caller selects a part, staff and voice; supplies a positioned chord progression and actual instrument button profile; and explicitly authorizes omission of other source pitches. Harmony is caller supplied, not inferred from the source.

For each source pitch, the result records its source address and either its melody target or an explicit omission. It also returns the resolved options, standard-bass requirement and generated note addresses with the selected bass/chord button IDs and their actual sounding MIDI pitches. The accompaniment uses sustained simultaneous bass and chord buttons. Omitted and added chord tones are allowed only when explicitly requested. This does not model an alternating accompaniment.

The original score is not changed. The implementation compares the selected melody's playback pitch, onset and duration in beats and seconds before returning success. It fails with diagnostics and no partial score or mappings if this comparison fails, the button profile cannot realize the harmony, or the selected source cannot be safely represented.

The original API accepts a monophonic, pitched melody voice with aligned measures, explicit harmony and a conservative MIDI range. For a voice containing chords, `model::standard_bass_pitch_selection::arrange_standard_bass_with_pitch_selection` and the full/viewer WASM export `arrange_standard_bass_with_pitch_selection(scoreJson, optionsJson, selectionsJson)` accept one explicit source note address and pitch index for every chord. Other pitches are recorded as omissions and require explicit authorization. Ties, accidentals and per-pitch fingering for the selected pitch are retained, and its playback must match an event from the original unmodified score. No highest-pitch or melody inference is performed. Tablature, transposing melody staves, linked views, typed spanners, unpitched notes, cross-staff melody, measure repeats and inconsistent measure structures are rejected. Repeated unisons within a chord, arpeggiated chord selections, automatic melody detection, phrase-level selection, standard-bass transitions and automated fingering are not implemented. A successful candidate still requires musical and performer review. The bounded search cannot establish that a rejected piece is unplayable.

## Screen button transitions

`model::standard_bass_transition::arrange_standard_bass_screened` and the full/viewer WASM export `arrange_standard_bass_screened(scoreJson, optionsJson, selectionsJson, policyJson)` generate the same candidate with explicit pitch choices, then screen its actual accompaniment attacks on the expanded playback timeline. The policy supplies a maximum position change in the profile's linear units and a minimum interval in milliseconds between successive attacks. The report lists each attack, the two button IDs, its playback time, the elapsed time and the greater of the two button-position changes. Repeats and endings are checked in playback order; tied continuation notes are not counted as new attacks.

Each attack must sound exactly the chosen simultaneous button pitches. Violating a limit, an unsupported playback situation, or a button/pitch mismatch returns a diagnostic and no partial score, mappings, actions or transition report. This screens the candidate chosen by the existing deterministic selection; failure does not prove that a different combination or accompaniment is impossible. Attack-to-attack time is not necessarily free movement time: notes can be held during that interval. Linear distance and onset spacing do not model hand shape, direction, finger changes, release time or instrument-specific physical reach. All results still require performer review.

When the initially chosen buttons exceed the movement limit, `model::standard_bass_button_search::arrange_standard_bass_find_buttons` and the full/viewer WASM export `arrange_standard_bass_find_buttons(scoreJson, optionsJson, selectionsJson, policyJson)` search for other profile buttons that produce the **same bass MIDI pitch and chord MIDI pitches**. The bounded search considers every adjacent attack in expanded playback order, including repeat-back edges, and reruns the normal transition screening on the result. It preserves the generated score and sounding pitches; the returned button actions may differ.

The search considers at most 256 independent written button regions, 32 equivalent candidates per region and 100,000 assignment attempts. A limit reports `transition-search-limit`, not impossibility. `no-same-sounding-button-path` means no path was found in this bounded exact-pitch model; other voicings, different rhythms and physical fingerings are outside its scope. It is not a fingering or movement-time certificate, and performer review remains required.

For instruments whose equivalent chord buttons use different octave voicings, the separate opt-in Rust API `arrange_standard_bass_find_voicings` and full/viewer WASM export of the same name allow another button when its actual bass MIDI note and chord pitch-class set match the original candidate. The button's octave doublings may differ. The generated score and action report contain the selected button's actual MIDI notes, so accompaniment playback and export change accordingly. Melody pitch, onset and duration are compared again after the change, and the normal playback-order button screening is reapplied. Candidates that change the chord's pitch classes or the bass note remain excluded, even if approximation was allowed for the initial harmony. The same search limits and performer-review requirements apply.
