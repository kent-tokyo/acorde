処理順は、`入力検証 → 和声候補 → 実発音区間 → ベース・旋律の制約 → 声部配置 → 音符出力 → 検証・候補選択` とする。段階2では和声位置から発音区間を作る。段階3では先取り後の区間を使って制約を取り直すため、前の和声のベースに新しい和音が重なる場合も判定できる。

2Aでは、発音区間全体を根音ベースが支えている場合だけ、自動ルートレスを許可する。一瞬だけ根音があっても支えとは数えない。ベースの最高音と旋律の最低音から伴奏の上下限を求め、必要なら既存のノード型に区間ごとの下限を追加する。タイ、楽器変更、移調、オッターヴァを反映し、ペダルなど持続時間へ影響する指定も確認する。解釈できない指定は箇所と理由を返す。

2Bの初版は元のパートを保持し、汎用の伴奏パートを追加する。対象外・ロック区間は追加パートを休符にする。音符生成では音名と変化記号を保持し、MIDI番号からの再推定で綴りを変えない。既存の標準ベース編曲は従来の入口を使う。

2Cの再現性は、生成UUIDを除いた音楽的内容と出典の一致で確認する。再読み込みで変わるIDと、旋律・テンポ・拍子などの内容変更を区別する。保存値からの復元時にも制約を検査し、識別用ハッシュを改ざん防止の保証とは扱わない。

現状の伴奏APIは、参照する旋律・ベースにペダル、装飾音、微分音などがあると型付きエラーを返す。先取りで反復の行き先が一意に定まらない場合も拒否する。これらは未対応範囲として公開し、自動候補選択でも無視しない。3Aのアクセントは既存の `Articulation` と再生処理を使い、通常の打鍵、強調した打鍵、タイの継続を区別する。

## 最初の成果物は旋律とコード進行を固定して比較する

初版では、旋律とコード進行を呼び出し側が指定する。コードの根音と基本的な長短を保ち、テンション、音の配置、伴奏リズムを変える。副属和音による置換と主旋律の編集は、それぞれ段階4・6で追加する。

入力には、元の `Score`、`ChordPlan`、対象小節、旋律・ベースの担当、楽器の音域、使用可能なテンション、先取り量、密度上限、ロックを渡す。初版の先取り量は四分音符の半分または4分の1、つまり8分音符または16分音符とする。拍子と実小節長に適合する位置だけを使う。

出力は編曲済みの `Score`、再現用の確定設定、採用・不採用の理由、変更箇所、各声部の配置と発音計画を含む。入口は `suggest_harmony_groove_arrangements`、再現入口は `replay_harmony_groove_arrangement` とし、Rust と full/viewer WASM に同じ意味の API を公開した。

比較案は次の3種類を初期設定とする。ラベルに対応する実際の音の違いを結果で確認する。

| 案 | 和声・配置 | リズム |
| --- | --- | --- |
| 素直 | 入力コードの明示的な省略を尊重し、通常は根音を含める | 拍頭中心、低密度 |
| 彩りを加える | 許可されたテンションとルートレス配置を使う | 最初の案と同じ打点を優先し、和声の効果を比較 |
| リズムを強める | 2案目の和声を優先する | 裏拍・先取り・休符の組み合わせを変える |

初版の上限案は32小節、64和声位置、1声部配置あたり32候補、全曲候補の実現128回、返却3〜5案とする。実測で不足が分かれば、件数と実行時間を併記して調整する。同じ入力・エンジン版・seed では同じ選択順にし、探索打ち切りと候補の不存在を区別する。3案を要求されても条件を満たす案が足りなければ、重複を埋めずに不足を報告する。

多様性の設定は、和声の複雑さ、発音密度、先取りの頻度、音域、編成、フレーズ末の静けさを独立した軸にする。プリセットはこれらの初期値をまとめたものとする。コードを簡素に保ちながらリズムを変える案や、テンションを加えながら音数を減らす案も選べるようにし、複雑さの増加だけを高評価にしない。

## 3案の自動選択には許可範囲と採否理由を持たせる

3Bでは、完成済みの3組の設定を呼び出し側に要求せず、一つの入力から候補を組み立てる。要求型 `HarmonyGrooveRequest` は、元の和声計画と共通制約に加え、和声位置ごとに追加可能な度数、許可する根音方針と声部数、先取りと発音密度の上限を持つ。個別指定用の `HarmonyArrangementRequest` は、選ばれた候補を実現するために内部で組み立てる。

テンションは各和声位置で「追加なし」を含む小さな候補集合から選ぶ。入力コードの根音・種類・既存の変化音・省略を保持し、初版の自動追加は許可された9・11・13度に限定する。三和音への7度の追加は行わない。全テンションを一度に足すと声部数や旋律との間隔を満たせないため、追加数を制限して実際の配置を検査する。

処理と判断は次の契約にする。

| 項目 | 初版で固定する挙動 |
| --- | --- |
| 候補順 | 「素直」を基準に、和声だけを変える「彩り」、その和声を優先して打点を変える「リズム」を探索。4・5案目は許可範囲内の別の組み合わせ |
| 制約 | 音域、旋律・ベースとの距離、既存の明示音、ロック、変更量上限を満たす。プリセットが呼び出し側の制約を書き換えない |
| テンション評価 | 発音が重なる音高・長さ・拍位置を使い、持続する旋律との摩擦や低域の密集に罰点を付ける。採用理由と罰点の内訳を返す |
| 先取り評価 | 実際に早めた区間でベースと旋律を取り直す。自動探索中の不適合候補は理由付きで除外し、明示指定の不正入力はエラーにする |
| 多様性 | 生成IDや案名を除いた音高・発音位置・音価・強弱を比較。和声差とリズム差を別々に示し、実発音が同じ案を重複採用しない |
| 上限 | 全曲を音符へ実現する試行は最大128回。32小節・64和声位置の上限とともに検査し、試行数と探索打ち切りを返す |
| 再現 | 元入力の識別情報、元の要求、選択済み和声計画・発音計画、契約版・エンジン版・seedを保存。再現時は候補探索をやり直さず、許可範囲を再検査して実現する |

「彩り」には基準案との音高の違い、「リズム」には打点または音価の違いを求める。発音が同じまま設定値だけ変わる場合は不足として報告する。構造上の違いが聴き分けられるかは3Cで確認する。

3Bの回帰例には、テンション追加が禁止された入力、声部数に必須音が収まらない入力、先取りできる境界がない入力、同じ候補へ収束する入力を含める。許可外の和音で件数を埋めない。元入力を変更した再現要求、未知の契約版、保存後に許可範囲を外れた設定も拒否する。

3Cは `tests/fixtures/arrangement/` に8小節・16小節の固定入力を置き、生成例を一つ用意する。各入力から元演奏と3案のScore JSON、確定設定、MusicXML、MSCZ、WAV、比較manifestを出力する。音源のSHA-256、プログラム番号、テンポ、音量、サンプルレート、残響末尾、生成元コミットをmanifestに記録する。比較用WAVは共通ゲインで生成し、案ごとに音圧を上げて印象を変えない。

## 和声の役割と楽器の発音能力を分けて扱う

汎用の和音展開には、開発版の `core::expand_harmony` を使う。コード記号から、根音、3度、5度、7度、テンションの音名と役割を得る。テンションをピッチクラスに変換する前に役割を保持し、9度と2度、13度と6度の配置上の違いを失わないようにする。

その結果を、一般的な鍵盤伴奏や自由ベース、標準ベースなどの実現処理へ渡す。標準ベースのボタンで出せない音は診断する。汎用のテンション追加が、既存のアコーディオン編曲を黙って別の演奏方式へ変えない契約にする。

メロディーとテンションの摩擦は、ジャンルの設定に応じて評価する。短2度や短9度をすべて禁止する規則にはせず、重なる音域、強拍か弱拍か、持続時間、解決先を使う。既定値は旋律の聴き取りやすさを優先する。

ルートレス配置では、同じ時間帯に低音を受け持つパートを調べる。自動設定は根音の支えがある場合に省略を選び、支えがない場合は根音付き配置を選ぶ。意図的に根音のない響きを求める設定も明示的に用意する。sus や omit3 の指定は、その和音の必須音規則として扱う。

声部接続は、各声部が次のどの音へ進むかを記録する。近くの音が存在するだけで滑らかと判定せず、声部交差、各声部の跳躍、共通音、3度・7度の進行を評価する。跳躍の許容値と平行進行の扱いはスタイルごとに選ぶ。

## 先取りは和声境界とロック境界をまたぐ編集として扱う

先取りされた音には「実際の開始位置」と「本来参照する和声位置」を保存する。例えば次小節頭の G7 を前小節4拍目裏から鳴らす場合、コード計画の G7 の位置は維持し、伴奏の発音だけを早める。

先取りした音を次の拍頭で打ち直すか、タイで保持するかを設定で選ぶ。先取りの区間に残る旧和声のベースや旋律との重なりも評価する。重複する打鍵、負の開始位置、小節の長さの不足、最後の小節から先の存在しない和声への参照を検査する。前小節がロックされているときは、そこへ音を持ち込む候補を採用しない。

反復では、書面上の次小節と実際の次の演奏先が異なる場合がある。全ての演奏順で同じ先取りが成立する場合にだけ共有の記譜へ書く。異なる先取りが必要なら、既存の演奏順展開を使って別の演奏譜へ出力する。初版で変換できない参照は理由を返して拒否する。

この処理に使う拍位置は有理数で保持し、音符へ分解する際に既存の対応グリッドを検査する。連符や弱起を丸めて帳尻を合わせない。

## 後続段階では技法の使いどころを指定できるようにする

段階4の副属和音は「どの和音へ進むか」を入力に持つ。例えば Am への到達を E7 で準備し、G♯ の綴りと A への進行を評価する。転調は到達する調と区間を指定し、共通和音を使う導入やドミナントからの導入を候補にする。指定した調への終止を含む区間を確認し、一つの変化和音だけを転調成立と数えない。

段階5では、共通のリズム計画にキックの打点、ベースが合わせる打点、休符、アクセント、音の保持時間を持たせる。ベースを全キックに一致させることは必須にしない。アプローチ音には到達するベース音を保存する。

ゴーストノートは、譜面の表示と発音の両方を設計する。ミュート音を持つ音源ではその奏法を使い、未対応の音源で短い弱音へ近似する場合は結果に明記する。既存の強弱記号だけで音単位の指定を保存できない場合、発音指定を表すモデル拡張を独立した変更にする。その際は `serde(default)`、コマンド、入出力、CHANGELOG、旧 JSON の読み込みを揃える。

段階6の主旋律編集は、変更可能な音の位置と音高・時刻それぞれの許可を入力にする。最初は音高を固定した先取りから始める。対旋律では既存のモチーフ変形を使い、フレーズ末の解決音と休符を指定する。タイや歌詞を持つ音は、それらの対応も保てる場合に限って編集する。

段階7では、和声、打点、ベース、音域、役割、曲の構成の差を既存の指標に追加する。音符が増えた数だけで候補を高く評価しない。局所編集には「この区間を薄く」「ここだけ先取り」「この和音を保つ」といった指定を使い、対象外の演奏イベントと記譜が変わらないことを確認する。

## 音色処理は再生側に置き、同じ楽譜を比較に使う

`core` は音符、奏法、演奏イベント、処理の指定を扱う。FM 合成や残響などの音声処理は再生層で実装する。既存の `PlaybackRoutingConfig` を接続点とし、共通の PCM 処理が必要なら任意依存の音声用 crate を追加する。配置は段階8の着手時に確定する。

FM エレピは、音源が持つプリセットの使用と、FM 合成器の実装を区別する。最初は同じ音源と設定で再現できるプリセットを使い、合成器を追加する場合は発振器・エンベロープ・強弱への反応を固定した設定を保存する。

デチューン、残響、サイドチェインは個別に無効化できる。サイドチェインでは、まず指定されたキック時刻を使った音量制御を実装する。音声信号を検出するコンプレッサーは次の追加単位とし、入力バス、検出方式、アタック、リリース、ゲインを保存する。

MusicXML・MSCZ で保証するのは音符・奏法・対応する楽器情報の範囲とする。独自の音源・エフェクト設定は別の再生設定に保存し、WAV と一緒に音源の識別情報を残す。効果の比較では音量を揃え、残響の末尾を含めて再生する。

## 検証は構造・ブラウザー・試聴の結果を記録する

段階0で、既存の開発用12作品と旧出力の所在・ハッシュを確認する。最初の成果物には、Cmaj9、Dm9、G13、ベース不在、旋律との接近、先取りとタイ、弱起、反復分岐、ロック境界の短い fixture を追加する。条件に合わず生成できない例も固定する。

各実装段階では、関連する意味のあるテストを追加したうえで、以下を完了条件とする。

- 元の旋律、ロックされた和声、編集対象外の記譜と再生を保持する。
- 小節の音価、音域、発音の重複、タイ、反復経路を検証する。
- 確定設定からの再現、入力変更の検出、失敗時に部分結果を返さないことを検証する。
- 記譜・再生が変わる段階では、MusicXML・MSCZ の往復を比較する。新しいテンションではコード記号の綴りと拡張指定も確認する。
- `cargo test --all`、`cargo clippy --all -- -D warnings`、書式確認を通す。macOS・Linux・Windows の結果を CI で確認する。
- full/viewer WASM を Chrome で実行し、ネイティブと音高・時刻・音価・強弱・確定設定を比較する。生成 UUID の一致は求めない。
- 探索回数、実行時間、最適化後の WASM サイズを、段階0で記録した同じ条件で比較する。CI のサイズ上限を変更する場合は、差分の根拠を残す。

最初の3案は8小節と16小節の開発例で試聴し、不自然な小節と担当パートを記録する。次の段階の受け入れにも同じ手順を使う。編曲の比較は同じテンポ・音源で行い、音色処理の比較は同じ演奏イベントで行う。

最終評価には、調・拍子・弱起・反復・旋律の音域が異なる未使用の6作品を用意する。既存計画の評価作品が未作成なら作成し、アルゴリズムと評価条件を固定するまで開発用に使わない。3人以上の聴き手が、旋律の聴き取りやすさ、フレーズのつながり、終止、演奏しやすさ、案の違いを確認する。

受け入れ基準案は、6作品中5作品以上で最初の4項目の中央値が5段階中4以上、6作品中4作品以上で新しい案への過半数の選好があることとする。案の違いは技法ごとの聴取結果を残す。基準と音源条件は評価前に確定する。未達の場合は結果を残し、その評価作品を再調整後の未知データとして数えない。

## 実装時の検証と未達時の扱いを固定する

最終コード `ff5e1c95` と文書更新後の `43d3c607` でPR #445のCIが通過し、8/16小節の試聴確認も記録した。段階0〜3の完了条件は満たしている。主作業ツリーの未コミット変更を巻き込まない。変更ごとに関連テストを通し、各段階の完了時に次を実行する。

```sh
cargo fmt --all -- --check
cargo test --all --locked
cargo test --workspace --all-features --locked
cargo clippy --workspace --all-features --all-targets --locked -- -D warnings
wasm-pack test --headless --chrome crates/wasm
wasm-pack test --headless --chrome crates/wasm --no-default-features --features viewer
```

macOS・Linux・WindowsのCIを照合し、full/viewerの最適化済みWASMサイズも同じツールチェーンで測定する。Apple Siliconでは `/Users/k_tanabe/.cargo/bin/wasm-pack` を使う。小さな差分の途中で全検証を繰り返す必要はないが、段階の完了記録には対象コミットと結果を揃える。

進捗は開発側の `docs/harmony-groove-progress.json` を更新し、各段階の状態、残作業、対象コミット、テスト結果、ログ・fixture・音源の識別情報を残す。3Cでは8小節・16小節それぞれの入力、3案の確定設定、発音差分、書き出しファイル、試聴記録をmanifestからたどれるようにする。試聴欄が空なら音楽的な受け入れは未完了とする。

| 未達・失敗の条件 | 次の扱い |
| --- | --- |
| 元旋律・ロック・タイ・反復・入出力が壊れる | 該当段階を修正し、失敗fixtureを回帰テストに加える |
| 音域や必須音が両立しない | 入力位置と制約を診断する。許可なく音を省略したり音域を広げたりしない |
| 探索予算を使い切る | 探索制限と試行件数を返す。候補不存在とは区別する |
| 異なる3案を生成できない | 不足を返す。固定した8/16小節の受け入れ例で起きた場合は3Bを未完了にする |
| CI・ブラウザー・サイズ測定が未確認 | 対応する検証を保留として残す。ローカル通過だけで段階完了にしない |
| 試聴で旋律が埋もれる、つながりが不自然 | 小節・パート・設定を記録し、該当する評価規則を修正して再比較する |
